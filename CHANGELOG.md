# Changelog

## v0.13.0

Minor release on top of v0.12.0 (fork pin v0.8.2 → v0.8.3). Its reason for existing is three fixes users hit in the field that had been sitting unreleased — a trust engine denying npm metadata against a version nobody asked for, a `cred_inject` composing a schemeless `Authorization` header, and a family of cross-checks that ran only in `openlock validate` and so never reached anyone who did not run it. Around those: a third harness, four new configuration surfaces, and a substantial repair of the project's own test and CI infrastructure, which had been producing greens that asserted nothing.

The connecting theme is narrower than v0.11.2's "silently did the wrong thing": here it is **a guard that exists but is not wired to the path it is supposed to guard**. The cross-checks were written and tested and never ran at sandbox create. Three shipped commands were dispatched but absent from the maps that drive discovery and `--help`. The base image pinned into each project was never re-evaluated after the CLI moved on. The nftables fence early-returned on every sandbox start because the binary it needs was not in the image. The live-integration suite leaked state that could only ever fail someone else's next run. Each was individually invisible, and none of them could be found by reading the thing that was broken — only by reading the caller that was missing.

### Added

- **`pi` (`@earendil-works/pi-coding-agent`) is a third harness (openlock-1ho).** Enum entry, launch argv, binary path, version pin, per-harness policy block and scaffold guidance. OpenRouter-only: openlock already stages `OPENROUTER_API_KEY`, which is exactly the variable `pi` reads, at a host the policy already allows. Anthropic deliberately does not extend to it — that plugin stages a Claude-Code-format OAuth credential *file*, which `pi` does not consume. Two hazards the type checker could not have caught were closed in passing. `harnessEnvFor` was a binary ternary on `claude_code`, so a third harness would silently have received no environment at all with no compiler signal; it is now an exhaustive `switch` over `Harness`, so the *next* harness fails to typecheck until handled. And `policyEndpoints` ignored its harness argument, emitting the `models.dev` rule unconditionally — that host is an opencode model-metadata dependency and `pi` ships built-in catalogs, so emitting it would have granted an egress domain the harness never uses. `pi`'s case sets `PI_OFFLINE=1`, suppressing its startup version check, telemetry and provider-catalog refresh: those fail closed against a default-deny policy, and one of the hosts involved could not be verified, so allowlisting was not an honest option. The package is the **scoped** name — the unscoped `pi-coding-agent` is a placeholder reservation at version 0.0.1 with zero dependencies, and pinning it would have produced a harness that installs cleanly and fails only at runtime.
- **`openlock providers models <id>` reports the model set a key is actually permitted to use (openlock-p60).** opencode's picker for openrouter lists OpenRouter's entire public catalog regardless of the configured key: measured on a real key, the picker offers 367 models while the authenticated `GET /api/v1/models/user` reports exactly 8. Nothing distinguishes them, and choosing a disallowed one returns `No endpoints available matching your guardrail restrictions and data policy` — which reads as an account or privacy fault rather than "not in your allowlist", and had already produced one wrong diagnosis. This is openlock's first host-side *authenticated* provider API call, so the fetch is an injected, **required** parameter with no default: no test can silently reach the network and spend the user's real key, and the real implementation is wired in at exactly one production call site. Per-entry tool capability is reported rather than any router-level grouping, because router is not a safe class — of the 5 routers that key permits, only `openrouter/auto` and `openrouter/auto-beta` declare tools support. `anthropic` reports unsupported-provider rather than an empty list, having no `models/user` equivalent.
- **Sandbox CPU and memory limits are configurable (openlock-251).** openlock set no resource limits anywhere, so every sandbox silently inherited openshell's own `cpu_limit=2`. Measured on a live container: `podman inspect` reported `NanoCpus=2000000000` and `CpuQuota/CpuPeriod=200000/100000` — 2.0 CPUs pinned on a machine provisioned with seven — and cgroup `cpu.stat` showed it had genuinely been throttled. A user who sized their machine generously got no benefit, with nothing in openlock's surface saying so. `cpu` and `memory` are optional manifest keys forwarded verbatim to `openshell sandbox create --cpu/--memory`; unset, no flag is emitted and openshell's default applies exactly as before, which a regression test pins so openlock cannot start silently imposing limits on everyone. The defect was the invisibility and the missing override, not the number 2, so no openlock default is invented. Found while investigating the reported TUI typing lag (openlock-21t) and measured **not** to be its cause — a controlled A/B across 1.0/2.0/6.0 CPU caps showed no dose-response in keystroke RTT and `nr_throttled` never moved during typing at any cap — so 21t stays open.
- **A credential's value can now be a literal (openlock-an3).** `cred_inject` can only inject a header whose value comes from a resolvable credential, and a credential's value could previously only come from a host environment variable. So injecting a *non-secret* literal header — an `anthropic-beta` feature-flag list, `anthropic-version`, a `user-agent` — meant either exporting it as a host env var purely to satisfy `from_env`, or having the in-sandbox caller send it, which only works when that caller is trusted to. `{ literal: VALUE }` joins `{ from_env: VAR }` as a second `CredentialSource` variant, exactly one required per value, returned verbatim with no trimming. Deliberately **no fork change**: the original proposal was a new `{ header, value }` shape on `cred_inject` itself, which would have cost a proto field in the 9000+ range, a Rust resolver branch, a `release/0.8` commit, a fork tag and a pin bump — none of it necessary, because `apply_cred_inject` has no notion of secret-versus-literal and openlock already owns the whole credential-provisioning pipeline. The wire format, proto, Rego rules and all Rust are untouched, so this adds no conflict surface to the next upstream sync. The honest limit is documented rather than glossed: a literal is still a `credentials:` entry provisioned as a generic-provider value, so it is committed verbatim and the docs warn against putting a real secret behind it. (`openlock report`'s redaction list skips literals for that reason, which is correct by construction and needed no change.)
- **`OPENLOCK_STATE_DIR` relocates openlock's state, and a relocated state dir gets its own gateway port (openlock-x8m8).** `GATEWAY_PORT` was a hardcoded 18081, so two correctly-isolated instances — a test harness, a CI job, a second checkout — could not coexist. The default state dir keeps 18081 **exactly**; deriving a port for it would have orphaned every running gateway, staled the `gateway_endpoint` recorded in the openshell registry, and made `doctor` and `docs/installation.md` report a port nothing listens on. Only a relocated state dir gets a derived port: sha256 of the resolved path mapped into 18082–18999, clear of both Linux's and macOS's ephemeral ranges. `XDG_STATE_HOME` is deliberately **not** honoured despite the XDG-shaped path, since anyone already exporting it would have their install silently relocated. State-dir resolution had been independently recomputed in three places and now routes through one `resolveStateDir()` — otherwise the override would have moved the gateway while leaving session storage behind.
- **A quickstart, a session walkthrough and a recipes page (openlock-cbc).** No end-to-end walkthrough existed; the README documented commands without ever showing a flow. Three narrative pages that weave the existing reference docs together rather than duplicating them. Written against the code, which turned out to disagree with the docs in several places — `docs/mounts.md` labelled its git-bundle example "(default / typical)" when bind is the actual default, so the two docs contradicted each other and the wrong one was the example a reader would copy (openlock-ypog); the README claimed `containers/` holds "Containerfiles for the four sandbox images" when there is one; it listed a `src/validate-policy/` that does not exist; and `prune-images` was missing from the command table. Things a new user hits that were documented nowhere are now stated: the fixed provider/harness pairing, that `openlock setup` hard-requires a TTY and cannot be scripted, the real flags on `logs`/`prune-images`/`sandbox`, and the full five-key global config schema. The walkthrough includes the benign egress denials a healthy Claude Code session produces, so a new user reading `openlock logs` does not conclude their sandbox is broken (openlock-q65). The Playwright recipe documents two silent failure modes — custom `RUN` steps placed before the harness sentinel are destroyed by `update-base`, and image builds have unrestricted network while runtime does not, so browsers must be baked in at build time — and sets `PLAYWRIGHT_BROWSERS_PATH`, without which Chromium installs into root's cache, which the uid-60000 runtime user cannot read, so the build succeeds and the agent fails at runtime.

### Fixed

- **A `cred_inject` whose `value_prefix` contradicts its provider is now a hard error (openlock-64dl).** Field-reported: a committed `.openlock/policy.yaml` whose `api.anthropic.com` `cred_inject` had no `value_prefix: 'Bearer '`. The anthropic provider stores the subscription OAuth token **raw**, precisely because the scheme is supposed to come from the policy, and the fork reads `value_prefix` with `unwrap_or_default()` and concatenates verbatim — so the sandbox shipped `Authorization: sk-ant-oat01-…`, upstream answered 401, and Claude Code treats a 401 as fatal, while `openlock validate` passed clean. This confirms H1 (stale, hand-drifted `policy.yaml`) from the 2026-07-31 gateway credential investigation, which had been recorded as unrefuted for lack of a witness. The mirror-image mistake is equally fatal and equally silent: openrouter stores `Bearer ` *inline* in the credential value, so adding a `value_prefix` there composes `Bearer Bearer sk-or-…`. Both are exact-equality violations of a spec openlock already owns in its provider registry, so neither needs a heuristic. It is a hard error rather than a warning because host, header and credential name all match a registered provider's own `policyEndpoints()` declaration and openlock itself wrote the stored value — there is exactly one correct prefix, a structural certainty. The one soft case is a `credentials:` bundle supplying the same name, whose value is user-supplied and may legitimately carry the prefix inline; that degrades to a warning. Declared prefixes are collected into a `Set` per (host, header, credential) triple rather than a single string, so two providers declaring the same triple differently cannot turn one of them into a false error. One test walks every harness's real `scaffoldPolicy()` output rather than a hand-written fixture, since the scaffold is the artifact that lands in a user's repo and then drifts.
- **Policy and config cross-checks now run at sandbox create, not only in `openlock validate` (openlock-j9t7).** `collectPolicyCrossCheckIssues` was called only from `lintFolder`, whose only caller was `validate` — so every cross-check, plus `policy.yaml`'s *schema* validation, was invisible to anyone who ran `openlock sandbox` without ever running `validate`. That is exactly how the value_prefix 401 above reached a colleague's terminal. Worth stating plainly: `policy.yaml` was not schema-validated at create at all, because nothing in the create path read policy content. One exported `collectConfigPolicyIssues` is now the single source of truth for "what is wrong with this config+policy pair", called by both surfaces; it deliberately replaces two hand-synced private collectors, since a separate create-path orchestration would have recreated this very bug. Severity is routed by whether the on-disk policy is actually about to be applied: fresh create and accepted `--rebuild` recreate **block**; a plain reattach only **warns**, because the running container keeps its already-baked policy and blocking there would lock a user out of a working session over a defect not live in it. The warning is re-emitted *after* the harness exits as well as before attach — printed only before, it was destroyed within a fraction of a second by the harness's full-screen TUI, so only `--no-attach`, non-TTY and scripted callers ever saw it. The double print is deliberate and commented so it does not get "cleaned up".
- **The fork pin moves to v0.8.3, ending a trust false-deny (openlock-1ft, openlock-pc5e).** The trust engine denied *versionless* npm packument requests by defaulting to whatever deps.dev's index happens to end on and then enforcing against it, permanently blocking metadata access for any package with one historically-critical version. Seen live in a colleague's egress log as `TRUST_DENIED @anthropic-ai/claude-code@2.1.98` — a version that has never been an openlock pin, because it was never requested. Enforcement is preserved for exact-version requests, and the install path always carries a real version. The same tag also fixes the bypass monitor, which probed `dmesg --version` rather than a real kernel ring-buffer read: under rootless podman the gate passed while the read failed `EPERM` and the child's stderr went to `/dev/null`, so dead bypass detection was indistinguishable from a quiet one. It now reports degraded once, with the reason. Before bumping, v0.8.3 was verified published (not draft or prerelease), with an asset list identical to v0.8.2's and the exact download URLs this file constructs returning 200 for darwin-arm64, linux-arm64 and linux-amd64.
- **`update-base`, `update-harness` and `prune-images` were invisible to tab-completion and `--help` (openlock-tuxj).** All three are real, dispatched commands in `cli.ts`'s switch, but neither `COMMAND_FLAGS` nor `COMMAND_DESCRIPTIONS` knew about them — and the completion generators and `printCmdHelp` both iterate those maps. They existed only in the hand-maintained `USAGE` string and in the dispatch switch. The durable half of the fix is the guard rather than the three entries: `COMMAND_FLAGS` now `satisfies Record<DescriptionCommandName, …>`, making "has a description but no flags entry" a compile error, and the test derives its expected command list from `cli.ts`'s actual `case "…":` labels instead of a second hand-typed array — which was itself an instance of the drift it was supposed to catch. A sanity-floor test pins known-stable anchors, so a degraded source parse fails instead of passing vacuously.
- **A gateway answering the port is no longer taken as proof of our own readiness (openlock-k5j2).** Gateway liveness derived *ownership* from port occupancy. In the exhibited bug an isolated-`$HOME` CLI found no PID file of its own, spawned a gateway that failed to bind because the real gateway already held `127.0.0.1:18081`, and then had its readiness `fetch` answered by that **foreign** gateway — so it printed "Gateway ready", wrote PID and driver files for a process that was already gone, and created a real podman container through someone else's gateway while the caller believed it was driving a separate docker-backed instance. The fix is attribution rather than driver comparison: after the readiness probe succeeds, if the child *we* spawned is no longer alive, a responding port is proof of foreign adoption. It needs no external tooling, so it works in CI, and it catches the general case of two isolated podman instances contending for the port, which a driver-mismatch check never would. `lsof` pid-ownership strengthens the signal where available. Two things were learned by probing a real gateway rather than reading source: `lsof -ti :18081` returns the listener **and every connected client**, so taking line 0 would have hard-failed against a healthy gateway with a live connection; and every HTTP path on the shipped gateway 404s with an empty body because that port speaks gRPC, so "improving" the readiness probe to `/health` would have made every `gateway start` hang 30s and fail. The bare `/` probe is left exactly as-is with a blunt comment saying a 404 *is* success here. The post-spawn refusal is hard; the already-running branch — which every user hits once a gateway is up — only warns, since there the evidence is a point-in-time `lsof` snapshot and `lsof` is not confirmed present on the CI runner. That path must never brick a working gateway.
- **A project pinned to a stale base image is now reported (openlock-x83q).** `openlock init` bakes the content-addressed base tag into each project's `.openlock/Containerfile` as a literal `FROM ghcr.io/vessux/openlock-base:<hash>`, so a change to `containers/base.Containerfile` reaches new projects only — existing ones keep building against the old hash, which still resolves cleanly because old ghcr tags are never deleted. Upgrading the CLI does not fix them and nothing said so. The nftables fix below is a live instance: every pre-existing project was silently stranded without it. A pure `detectBaseImageDrift()` is now surfaced in `openlock doctor` **and** in the `openlock sandbox` preflight, so it cannot be missed by someone who never runs doctor. It warns and never blocks — the stale pin builds fine and may be deliberate — and names the remedy rather than merely reporting a mismatch. A custom or unparseable `FROM` line renders as an explicit `ok:true` detail, so "not comparable" stays visibly distinct from "not an openlock project".
- **nftables is installed in the base image, so the netns fence can fast-fail (openlock-jsfo).** Without it the supervisor's `find_nft()` returned `None` and `install_bypass_rules()` early-returned on every sandbox start, logging `nft not found` — the `openshell_bypass` inet table was never created. Measured on Mac/podman before the fix, from **inside** the fenced workload netns (which matters: `podman exec` with no flags lands in pid1's *outer* netns, which has full connectivity, so testing there would falsely suggest an open egress path), a direct connection to a raw IP timed out rather than being refused. So there was no open egress path — the severity framing is confirmed, not contradicted — but the connection black-holed instead of fast-failing. This does **not** restore bypass detection, which was broken for an independent reason nftables cannot fix, now fixed fork-side in v0.8.3 above. **Migration:** this does not reach existing projects automatically; run `openlock update-base --project <dir>` and force a sandbox-image rebuild.
- **Concurrent `openlock sandbox` invocations no longer each run a full base build (openlock-jyk).** Two of them both saw `imageExists === false` and both re-downloaded Node and uv, because only a *successful* build tags an image and a failed one leaves the tag absent exactly as before the attempt — nothing marked "build in progress". `src/lock.ts` adds a genuinely cross-**process** mutex; in-process memoization cannot address this, since the motivating case is separate OS processes with no shared memory. Bun and `node:fs` expose no `flock(2)` binding, so the lock is a file published atomically by writing `{pid, token}` to a private temp path and `link(2)`-ing it into place — `link` fails `EEXIST` if the target exists, which makes it both the exclusive create and a guarantee that the content is complete the instant the file becomes visible. Stale locks are reclaimed when the recorded holder PID is dead or the file's real age exceeds `staleMs`; both the PID-reuse false negative and the wrongly-reclaimed-slow-holder case are documented rather than papered over, and the worst outcome of either is one extra concurrent build, never data loss. `staleMs` (15m) sits deliberately below `timeoutMs` (20m) so a legitimately slow first build degrades to today's behaviour instead of becoming a new hard failure. The bug report's premise about *where* the race lives was corrected in passing: `ensureImage` has no production caller at all — the real path is `session.ts` → `ensureSandbox`, which had two unlocked check-then-build sites of its own, and the Node/uv download happens in `ensureBase`. All three are now locked, each keeping its unlocked fast path so the common already-built case never touches a lock file.
- **A transient TLS blip no longer fails the whole base image build (openlock-jp2).** Both external fetches (Node, uv) had no retry. Observed on a live-integration job: three sequential builds of the same content-hash tag, two killed by `curl: (35) Recv failure` at the Node layer, each failing a different otherwise-unrelated test before the third succeeded. The originally-reported cause — tests racing to build concurrently — is not what happened, since `bun test` runs those files sequentially in one process; the real amplifier is that a failed build leaves the tag absent, so every later test reaching `ensureImage` stacks another independent roll of the dice inside one short outage. `--retry-all-errors` is the flag that makes curl retry a connection reset (plain `--retry` covers only transient HTTP codes). The `sha256sum` verification after each fetch is unchanged and remains the backstop.
- **`uninstall.sh` now resolves a `bun link` install and never strands the gateway (openlock-ujv).** It resolved the binary only as `${OPENLOCK_INSTALL_DIR:-$HOME/.local/bin}/openlock` and never consulted `PATH`, so a dev install at `~/.cache/.bun/bin/openlock` failed the usability guard and took the degraded path: `clean --all`, `prune-images` and `gateway stop` never ran while the script still reported "openlock purge complete." Observed 2026-07-31 — the gateway survived a `--purge`, and 5 containers plus 15 volumes would have been orphaned had the podman machine not been recreated separately. The leftover gateway still holds provider rows in `gateway.db`, so "uninstall and reinstall for a clean slate" lands the user in exactly the stale-credential state openlock-9ej describes. It now falls back to `command -v openlock`, stops the gateway from its pid file regardless of whether the binary is usable (validating that the pid is numeric, live, and has a matching command line, so a recycled pid is not killed), and **waits** for the gateway to exit before removing state — escalating to `SIGKILL` after 3s rather than proceeding, because a warning that continues anyway reproduces the same silent half-purge. `--dry-run` also stops claiming it would remove a binary that does not exist.
- **A tool-incapable OpenRouter model is caught before opencode launches (openlock-4g1).** A fresh opencode+openrouter sandbox let opencode pick its own model from the full public catalog with no regard for tool support; it picked an image model and the first prompt died with `No endpoints found that support tool use`. The enabling observation is that capability and permission are different questions with different sources: whether a model *supports* tools is public, on `supported_parameters` from the unauthenticated catalog, so it can be checked with no credential and no new trust surface, while whether the key is *allowed* to use it needs the credential and is `providers models` above. A configured model the catalog says lacks `tools` now **blocks** the launch with a message naming the real cause; no model configured **warns** and proceeds, deliberately not blocking, because a block would forbid launching and then picking interactively in opencode's own TUI, which works today. A lookup failure or unrecognised id also warns and proceeds — neither is evidence a model lacks tool support, only that openlock could not check, and openlock must stay usable offline. Resolution tries the literal id first, then one stripped leading `openrouter/`; the order is load-bearing, because opencode addresses models as `<provider>/<openrouter-id>` so scaffolded ids carry a prefix ordinary catalog ids lack, while the 6 router aliases genuinely contain the segment in their own id. Literal-first is correct for both shapes.
- **Both gateway abort paths now clean up the state files they wrote (openlock-u60k).** `waitForGatewayReady` has two paths that abort a start it had already written pid, driver and port files for, and they disagreed: the foreign-adoption refusal unlinked all three, while the generic "exited unexpectedly" branch left them behind describing a process that never started. One `clearGatewayStateFiles` now serves both, plus `stopGateway`, which held an identical third copy. Impact is low and the code says so — every reader re-checks `pidAlive()` first, so a stale pid file is inert — but the inconsistency was discoverable only by reading both paths. Deliberately not applied to the 30s-timeout branch, which can fire with the child still alive; removing the pid file there would orphan a live gateway.

### Changed

- **Pinned agent CLIs moved to claude-code 2.1.224, opencode 1.18.18 and pi 0.84.2.** Each was live-verified in a sandbox with real inference round-tripping, rather than only building — see *Verified* below.
- **CodeQL runs on every pull request, not only PRs based on `main` (openlock-129).** `CodeQL` and `Analyze (javascript-typescript)` are required status checks, but `codeql.yml` filtered its `pull_request` trigger to `branches: [main]`, so only a PR based directly on main could ever run them. That makes stacked PRs unmergeable: in a stack each layer is based on the layer below, so every layer above the bottom sits permanently on "waiting for Code Scanning results" for a check that will never fire. Hit for real on stack #128, where the bottom and top PRs reported clean while the three middle ones could not be merged at all. The cost of dropping the filter is CodeQL runs on PRs targeting a non-main branch, which is precisely the point.
- **The base image builds on `main` pushes that touch `base.Containerfile` (openlock-6qfr).** `base-image.yml` triggered on release tags only, so a `base.Containerfile` change landing on main left its content-addressed tag unbuilt until the next release — and in that window every live-integration run and every fresh install paid a full local rebuild instead of a cheap pull. The existing idempotency check already skips the build when the tag is present, so the marginal cost is one `imagetools inspect`. The tag trigger is unaffected: GitHub does not evaluate `paths:` filters for tag pushes, which is called out in the file because the combination looks like a bug and "fixing" it would be release-breaking. The misleading log line that sent diagnosis the wrong way is also framed now — `ensureBase` is `imageExists → tryPull → local build`, so podman's raw `manifest unknown` on an unpublished hash is expected and non-fatal, but `tryPull` inherits stderr, so that error reached the log with nothing saying a local build follows.

### Testing and CI

The live-integration suite was not idempotent, and several of its greens asserted nothing. That is its own defect class in a project whose changes are mostly about failure modes.

- **The live suite now cleans up unconditionally (openlock-18c).** A *passing* run left 4 providers and 4 sandboxes behind in the dev gateway, and the next run then failed 3 tests with "provider already exists" and transport errors that read like product defects — it had already cost a real misdiagnosis. Two mechanisms were at fault. Cleanup lived in an in-body `try/finally`, and on a bun test timeout `afterEach`/`afterAll` run but an in-body `finally` does **not**, so a timed-out network test leaked its sandbox entirely. And four files did a raw `podman rm -f` and never `sandbox delete`, so the gateway's own record survived even a clean run — that leaked record is what kept the provider "attached to sandbox(es)" and undeletable. Teardown is a per-test **registry**, never a prefix sweep: names are registered by the test body as it creates them and only those exact names are ever deleted, because a blind `ol-*` sweep would run against the developer's real dev gateway holding their real credential provider. The hooks carry an explicit 120s timeout, since hooks do not inherit an `it`'s budget and bun defaults an `afterAll` to 5000ms — without it the hook was cut off mid-delete and leaked anyway, the timeout partially defeating the fix it was part of.
- **Teardown waits for the delete to actually land (openlock-18c, openlock-qaed).** `openshell sandbox delete` is asynchronous: exit 0 means the gateway *accepted* the delete, not that it completed, so sandbox-before-provider ordering is necessary but not sufficient. Teardown polls `getSandboxState` until it reports `missing`, reusing that function specifically because it already discriminates a genuine not-found from "unreachable". One file — `npm-scoped-pkg.test.ts` — never received the fix at all, because the pattern had been copy-pasted inline into each file and there was nothing to fall through to; that is what kept the gateway-clean check red on main since #149. The machinery is now extracted into one helper and all six files migrated to it, so the class is fixed rather than the instance. **Docker's leg passed throughout both of these bugs**, because docker teardown lands fast enough to win the race — for teardown and lifecycle work a green docker leg is not evidence, and podman is the primary runtime.
- **CI asserts the gateway is clean after the suite (openlock-n73d).** Nothing verified that the teardown fix keeps working, and no existing signal could: every CI run starts from a *fresh* gateway, so it structurally cannot detect a leak, which only manifests on a second run sharing state — and locally `bun run test` skips the suite entirely. A read-only post-test step now fails the job with the leaked names printed. It is deliberately an assertion and **never** a delete sweep, since the suite also runs against a developer's real dev gateway and a step that deletes on match is a sweep with a different name. The prefixes are derived from the suite itself rather than invented, so the filter matches real residue instead of silently never matching — the failure mode that would have made this a permanent false green.
- **Compiled-binary exit behaviour is guarded in two labelled tiers (openlock-r19).** `bun run` auto-exits when a script's body finishes; a `bun build --compile`d binary does not — it stays alive until the event loop drains. So a dangling handle is invisible to every existing test in this repo and hangs the shipped binary, a class that has bitten twice. Tier A is hermetic and runs in the required `test` job, compiling the binary and asserting the no-infra commands exit within a self-enforced timeout; its header states plainly that it would **not** have caught either historical bug, both of which need real infrastructure. Tier B is live-gated and reproduces #26's exact path, deliberately forcing the fresh-spawn branch because `startGateway()` early-returns when a gateway is already up, and reusing a running one would produce a green that never touched the broken code. Both run the binary with stdio fully piped, never inherited or a TTY: a long-lived child holding the parent's inherited stdout fd hangs specifically the piped/CI capture path, so a TTY-attached run can pass while the real path hangs.
- **A live test that could clobber the real openshell registry now cannot (openlock-tv6u, openlock-x8m8).** The gateway-collision test relocated `OPENLOCK_STATE_DIR` but not `XDG_CONFIG_HOME`, and `registerGatewayMetadata` writes under a **fixed** gateway name — so the throwaway gateway registered itself into the shared registry and repointed it at a scratch port that died with the test. Observed live: the developer's registry left on port 18156 while the real gateway listened on 18081, breaking every later command with "Connection refused". Both gateways now override `XDG_CONFIG_HOME` too, and a guard snapshots the real registry file and asserts it byte-identical afterwards in a `finally`, resolving the real path *before* any override is installed and importing `GATEWAY_NAME` rather than re-literalling it. `docs/installation.md` gains the matching caveat, having previously implied more isolation than `OPENLOCK_STATE_DIR` delivers.
- **`OPENLOCK_CONFIG_DIR` is a test seam for credential and global-config resolution (openlock-6pwu).** A live test deleted the operator's real `credentials.json` — the second live-credential loss in this project. The structural cause is that there was no way to point openlock's own credential resolution at throwaway state, so a test that must satisfy `hasCredentials()` had to back up, mutate and restore the real file, and every such test reinvented that flag discipline. When set and non-empty the variable **is** the config directory, used as-is; unset, behaviour is byte-for-byte what it was, pinned by explicit no-regression tests for both branches. It is an env var rather than dependency injection because it has to survive a process boundary — the compiled binary is spawned as a child, so its module graph is unreachable from the parent. It is **not** `XDG_CONFIG_HOME`, because podman honours that for its own config and the spawned child inherits it: a fake value makes `podman machine list` return an empty table with a real machine running (measured on macOS; the constraint is macOS-specific, since Linux rootless podman has no machine layer). An active override prints a loud one-time stderr notice — silence is the failure mode being guarded against — on stderr specifically, never stdout, because several tests assert stdout byte-for-byte. What it does **not** isolate is documented at the resolver: the gateway registry, gateway provider records and the state dir, because partial isolation that reads as complete is its own hazard.
- **`OPENLOCK_DISPOSABLE_HOST` is a fail-closed marker for tests that genuinely cannot use synthetic state (openlock-o4t4).** Some tests need the real compiled binary, real podman and a real gateway, and the policy is that those must never point at real user data. No VM is provisioned, because none is needed: the live-integration runner already **is** a disposable host — a throwaway ubuntu-24.04 with a fresh `$HOME` and nothing of an operator's on it. Only the exact string `1` counts, so an unrecognised value refuses rather than guesses; `requireDisposableHost()` throws rather than skipping, and never falls back to backup-and-restore of real state, since "has a backup" was already read once here as a confirmed-safe signal and it deleted live credentials. Its error message is written for someone hitting it on their own laptop, and specifically warns against setting the variable to make the error go away. The guard is the point of the PR: a gated test that silently stops running is a permanent false green, so a dedicated test turns a dropped marker into a red, and it lives under `tests/integration/` because that is the only directory the job it guards actually runs.
- **The `test` job stopped running bare `bun test`, and gained a script it had been missing (openlock-lpc).** Bare `bun test` was safe only by accident — `openshell-fork/` is gitignored and so absent from a CI checkout — and contradicts the project's own never-bare rule. Swapping it to `bun run test` alone would have **dropped** `scripts/render-default-policies.test.ts` from CI, a fixture-drift guard and the one class of test this project has been burned by twice, because the scoped script covered only `./src/` and `./tests/`; the glob widens to include `./scripts/` in the same commit. Separately, live-integration now HEAD-checks the pinned fork's release assets right after `bun install`, failing in seconds rather than 404-ing ten minutes in after podman setup, which is what a release PR that bumps the pin used to do. Fail-fast was chosen over skip-on-404 deliberately: to `curl -f`, "not published yet" and "asset renamed or broken" are byte-identical, so a skip would silently swallow the second case forever.
- **`waitForSandboxReady`'s tests no longer measure the machine (openlock-ur15).** They asserted real elapsed milliseconds and burned real `Bun.sleep(500)` ticks plus two subprocess spawns per iteration; under full parallel load the `toBeLessThan(2000)` bounds were observed blown at 5–12s, and `test` is a required check, so the flake blocked merges for reasons unrelated to the diff. An optional now/sleep seam defaults to the real clock so production behaviour is unchanged, and the assertions now state the property they were actually protecting — "slept at least once", "zero sleeps" — rather than a wall-clock bound. Both halves of the seam are required: faking only `sleep` while `deadline` still read the real clock would have made the timeout tests busy-spin.
- **Three `validate` lint limits are now documented and pinned rather than silently accepted (openlock-ztf).** The `.gitignore` advisory only ever inspects `.openlock/.gitignore`, so it over-warns for a user who ignores `config.local.yaml` from a parent — reworded to state precisely what was inspected, rather than adopting `git check-ignore` and adding a subprocess plus repo detection to a command that is currently pure `existsSync`/`readFileSync` and works fine outside a git repo. Cross-file collision issues carry the merged array's index and unconditionally name `config.local.yaml` even when one side genuinely lives in `config.yaml`; not fixed, since attributing an index needs per-mount provenance threaded through the merge, but now commented and pinned by a test that must be consciously updated by any future fix. And the dedup key has no path component, so a within-file duplicate can mask a cross-file one for a single cycle — benign and self-resolving. All three are named as pinning **documented, accepted** current behaviour, not a desired end state.
- **The security doc's host-exec bypass claim was overstated and is corrected (openlock-dx7).** It said a host-side `podman exec` lands in the container netns "without proxy enforcement, so egress policy, `cred_inject`, and the per-binary credential gate do not apply" — which reads as free egress, and is wrong about egress. Verified in the fork source rather than inferred: the netns-scoped bypass ruleset accepts only the proxy address, `oifname lo` and established traffic, then rejects, and nothing in it matches on socket owner — so an exec-injected process traverses the same chain and its direct egress is rejected exactly like a cooperative in-sandbox bypass. The obvious way this could have been wrong was checked: the *sibling* sidecar ruleset does match owner, and had openlock been installing that variant, `podman exec -u <proxy_uid>` would be a genuine unfenced bypass — it is reachable only from the Kubernetes sidecar topology, which openlock never selects. What such a process genuinely escapes is now stated with the reason: `cred_inject` and the per-binary gate (both need the supervisor's proxy env, which a `podman exec`'d process never inherits), non-network access (no packet exists, so nftables has nothing to see), and namespace injection below `podman exec` — measured, with three `nsenter` injections producing zero podman events while a control `podman exec` in the same window fired its expected pair, proving the listener was live and the gap real. Users are also told, for the first time, that the fence's rejection log is best-effort and surfaced nowhere, so a bypass can be enforced with no visible trail.

## v0.12.0

Minor release on top of v0.11.2 (fork pin unchanged at v0.8.2 — no new fork commits). Adds harness version management, moves the pinned agent CLIs forward, and fixes a credential-replacement gap plus two papercuts that a from-scratch install walks straight into.

### Added

- **Harness versions are pinned in one place, and `openlock update-harness` proposes the bump (openlock-bcr).** The npm version of each in-sandbox agent CLI was previously embedded in the seed-Containerfile builder and duplicated across its snapshot fixtures, so moving a pin meant hand-editing several files and regenerating snapshots — a chore dull enough to be deferred, which is how a pin goes stale. `src/sandbox/harness-versions.ts` is now the single source of truth; the version became an *argument* to the Containerfile renderer, so the fixtures render a fake sentinel and stop churning on every bump. `openlock update-harness` resolves each harness's npm dist-tag and reports or applies the change, and `bun run harness:check` gives CI the same signal. The resolution target is deliberately per-harness rather than one shared tag: `@anthropic-ai/claude-code` publishes a curated `stable`, while `opencode-ai` publishes no `stable` tag at all, only `latest` plus snapshots.
- **A clean-reinstall guide in `docs/installation.md`.** Reinstalling the binary does not give you a clean slate: `uninstall.sh` deliberately preserves `~/.local/state/openlock/gateway.db`, and that database holds the credential rows actually injected into sandboxes. So the uninstall/reinstall cycle someone runs *because* authentication is misbehaving is precisely the one that preserves the offending state — only `--purge` clears it. The guide covers the teardown ordering (the gateway is a host process on port 18081 that outlives the state directory it was started from, so it is stopped first and explicitly), what to back up beforehand, and the podman resources a purge does not reclaim.

### Changed

- **Pinned agent CLIs moved to claude-code 2.1.212 and opencode 1.18.9 (openlock-nna).** Both were live-verified in a sandbox — real inference round-tripped on each harness — rather than only building. The staged `.claude.json` onboarding shape was re-verified unchanged against Claude Code 2.1.212, so it has now survived 84 patch releases; that shape has no test that can catch its regression (the assertion is on our own staged string, not on CC's behaviour), which is why it is re-checked against a live startup at each bump.

### Fixed

- **A stale gateway credential can now be replaced (openlock-9ej).** `openlock login` writes only `~/.config/openlock/credentials.json`; the copy a sandbox actually receives is the gateway's, seeded later by `ensureProvider` and gated by never-clobber — which fired only on an *expired* credential. With a live-by-the-clock gateway row, a fresh interactive login was therefore a complete no-op at the gateway, and there was no supported way out: no `--force` on `login`, and `logout` removed only the local record. openlock now pushes when the host token is strictly newer than the gateway's, comparing the host's `access_expires_at` against the gateway's `credential_expires_at_ms`. Both come from the same issuer with the same TTL, so a later expiry means a later mint — which keeps never-clobber intact in the direction it exists for, since a worker-refreshed token always carries the later expiry and is never overwritten. `openlock logout` now clears the gateway row as well.
- **The wedged-credential recovery path could never have run (openlock-45h).** `seedRefreshProvider` issued `provider create` on *both* push paths, but the gateway persists `CreateProvider` with `MustCreate` and answers `already_exists` — so the only automatic repair for a credential the refresh worker could no longer renew threw on every retry instead of self-healing. It now selects create-or-update from whether the provider exists, mirroring the generic branch beside it. The existing tests concealed this by mocking `provider create` as a success while asserting it was called; the mock now refuses create-on-existing exactly as the gateway does.
- **Credential remediation named a command that install.sh users do not have (openlock-17q).** The failure text pointed at `cd openshell-fork && mise exec -- openshell provider delete <id>`, a path that exists only in a development checkout — for everyone else the fork binary lives under `~/.cache/openlock/bin/<tag>/`. The message is now rendered from the same resolver `ensureProvider` itself uses.
- **`openlock exec <s> -- claude ...` reported "Not logged in · Please run /login" on a healthy install (openlock-04x).** The attach path sets `CLAUDE_CONFIG_DIR` so Claude Code can find its staged credentials; the exec path injected no environment at all, so CC looked in `$HOME` and found nothing. The consequence went beyond ergonomics: that string is the same first line as a genuine credential failure minus the `401`, so reaching for `openlock exec` while debugging authentication returned a false confirmation of a bug that was not there. Both paths now call one shared `harnessEnvFor`, since the drift between them was the defect, and exec reads the harness from the session record rather than assuming `claude_code`.
- **`openlock doctor` exited 1 on a healthy machine (openlock-ucm).** Readiness was probed for every *installed* runtime, so a Docker CLI on `PATH` without a running daemon — the default state on any Mac with Docker Desktop installed but not launched — failed `docker daemon reachable` while podman, the runtime openlock had actually resolved, was entirely green. That is the documented golden path's first command reporting failure on a working machine, and it halts any scripted `openlock doctor && openlock init ...`. Readiness now gates on the resolved runtime; other installed runtimes report presence informationally. The same latent bug was fixed in the subuid and gateway-reachability probes, the latter of which spins up a real podman container. When several runtimes are installed and none is selected, readiness still runs for all of them but can only *warn* — skipping the probes outright would trade a false failure for a false pass, leaving a fresh user with a stopped podman machine a green doctor followed by a failing `openlock sandbox`. A test drives the result through the real renderer and asserts zero failures, so the exit-code contract is pinned rather than assumed.
- **The `global config` check reported success for a file that did not exist.** An absent global config is legitimately not an error — defaults apply — but the check's label embeds the path, so rendering green read as "found and valid". The pass/fail bit is unchanged; the detail line now states which of the two it actually found.

### Verified

- **The golden path was re-walked from a genuinely empty machine, not merely tested.** Full state purge, development install unlinked, podman machine destroyed and recreated, then `install.sh` → `doctor` → `init` → `validate` → `sandbox` as a new user, ending in real inference through the gateway with `cred_inject` — checked against a computed answer rather than an echo, so a passthrough could not masquerade as success. Both papercuts above were found *during* that walk and re-verified fixed on the same machine: `doctor` exits 0 with the unused runtime reported as informational, and `openlock exec -- claude` returns a correct answer with no manual environment wrapper.
- **The wedged-credential repair (openlock-45h) was exercised against a real gateway,** not only against its mock. A live provider row in exactly the failing state — expired credential, refresh worker reporting `error` after the token endpoint returned HTTP 400 — was re-pushed successfully instead of failing with `already_exists`.

## v0.11.2

Bugfix release on top of v0.11.1 (fork pin unchanged at v0.8.2 — no new fork commits). Closes out the two verification gaps left open by the v0.11.1 investigation and clears a family of related defects: cases where openlock did the wrong thing *silently*, with every status surface reporting success.

### Added

- **`openlock validate` warns when a policy endpoint allows a credential-bearing host but declares no `cred_inject` (openlock-s15).** `cred_inject` is a per-endpoint field and is never inherited, so adding a host to unblock a connection error silently forwards the in-sandbox *placeholder* credential; upstream answers `401`, and agent harnesses treat a 401 as fatal while tolerating a blocked connection — which makes allow-without-inject strictly worse than denying. The lint fires when an endpoint shares its host with another endpoint in the same `network_policy` that does inject, or when the host is a known provider credential domain (derived from the provider registry, not a hardcoded list). It is a new non-blocking `warning` severity, so `validate`'s exit code is unchanged: host matching is heuristic, and an intentionally-public path on an otherwise credentialed host is legitimate. This is the static check that would have caught v0.11.1's own openlock-z08 before release, and the same class of mistake as GH #79.

### Fixed

- **`openlock exec <name> -- <cmd>` silently did nothing when the command's own arguments contained `-v` or `--version` (openlock-j9d).** The pre-dispatch scan in `cli.ts` tested the *entire* argv with `includes()`, ignoring the `--` separator that marks "everything after this belongs to the command inside the sandbox" — so openlock printed its own version and exited **0** without ever running the command. `-v` is what made this serious rather than a curiosity: `openlock exec X -- rm -v file`, `-- ssh -v host`, and `-- grep -v pat file` all no-opped with a success exit code, which a script or an unattended run cannot detect. `--print-base-tag` shared the flaw; `--help`/`-h` did not, since it only ever tested the first argument.
- **An explicit `OPENLOCK_RUNTIME=docker` could silently run on a podman gateway (openlock-ox1).** Whether to reuse a running gateway was decided from PID liveness alone, never checking which driver that gateway was started with — so the requested runtime was silently ignored and the sandbox was created on whichever driver happened to be up, invisibly. The driver is now recorded alongside the gateway PID, and a mismatch is a hard error naming both drivers and pointing at `openlock gateway stop`. The gateway is deliberately not restarted automatically, since that would tear down sandboxes belonging to the running driver. A gateway started before this release records no driver, which reads as "unknown" and never errors. The active driver is also now shown in `openlock gateway status` and as a `DRIVER` column in `openlock list` — its invisibility is what let the mismatch go unnoticed, and it was found only because it nearly produced a false pass while verifying the fork's SELinux docker leg.
- **A gateway that is down no longer makes every session look deleted (openlock-vtl).** `getSandboxState` mapped *any* non-zero exit of `openshell sandbox get` to "missing", and a transport error is exactly a non-zero exit — so "gateway unreachable" and "this sandbox does not exist" were indistinguishable. Transport failure is now its own `unreachable` state, discriminated on stderr shape using the same predicate `deleteSandbox` already applied (now shared, so the two cannot drift). `openlock clean --stale`/`--all` refuse unreachable sessions and name what they skipped; `openlock list` reports `(gateway unreachable)` instead of claiming `(no container)`; and reattach fails fast naming the gateway rather than reporting `has no container; run openlock clean to reclaim` — advice which, if acted on, would have destroyed a healthy container. `openlock stop` and the idle reaper were audited and were already safe, since both require a `running` state to target anything. The destructive exposure was already closed in v0.11.0 by healing the gateway before classification; this fixes the underlying conflation.
- **A sandbox being torn down no longer burns the full readiness timeout (openlock-ddd).** Phase `Deleting` was folded into the keep-polling bucket, so the readiness wait polled a doomed sandbox for its entire 60s (90s on resume) budget and then reported a generic "did not reach Ready state" instead of the knowable cause. It now fails fast with `sandbox <name> is being deleted`. `Provisioning` and `Unknown` deliberately keep polling — the driver being unable to determine state is not proof of death.
- **`openlock doctor` no longer silently deletes a legacy credentials file (openlock-cjr).** `readCredentials()` detected a legacy V1 file and truncated it as a side effect — a read-shaped function destroying credential material with no backup and no notice, triggered even by purely informational reads. The original is now preserved alongside the migrated file (mode `0600`), and the user is told where it went and to re-run `openlock login`. The backup is written and read back for verification *before* the original is touched, so a failed backup aborts the migration rather than truncating on the strength of an unverified copy — which does mean a genuinely broken write now surfaces as an error instead of as silent data loss.
- **A `credentials:` bundle added to an existing session is now flagged instead of failing closed at egress (openlock-04t).** Providers attach only at sandbox *create* time; reattach can re-provision the gateway-side record but cannot attach a new bundle to an existing container. So adding a credential to a live project and re-running `openlock sandbox` produced the worst possible shape: gateway provider created, `openlock validate` passing, every surface healthy — and `cred_inject` for that bundle failing closed at egress with no openlock-side signal. The attached bundle set is now recorded at create time and compared on reattach, warning on every reattach until the session is recreated and pointing at `openlock clean <name>`. Sessions created before this release carry no recorded set; that is treated as "unknown, cannot compare" and never warns, so no pre-existing session raises a spurious alarm.
- **The local sandbox JWT's never-expire behaviour is now pinned rather than inherited (openlock-4b1).** `ttl_secs = 0` was a *fork default* openlock had never asserted, so a future upstream sync flipping that default would have silently resurrected GH #75 — a sandbox stopped for more than an hour failing to resume with `ExpiredSignature`. The generated gateway config now sets it explicitly. The pin is verifiable rather than decorative: the fork's config struct denies unknown fields, so a wrong key name fails gateway startup loudly instead of being ignored.

### Changed

- **`bun.lock` is now tracked, and CI installs are frozen (openlock-hes).** The lockfile was gitignored and all four CI install steps ran a bare `bun install`, so with caret ranges every install resolved dependency versions independently — neither CI nor a user could reproduce the tree a release was built and tested against. This was not theoretical: it is how js-yaml 5.2.2 reached a working tree past a `^4.1.0` pin and broke every CLI invocation with `Missing 'default' export in module js-yaml.mjs`, and js-yaml drifted 4.1.1 → 4.3.0 across a single session's reinstalls. **Contributor-facing:** CI now runs `bun install --frozen-lockfile`, so a dependency change requires committing the updated `bun.lock` or CI fails. Dependabot is also configured to ignore js-yaml major bumps, since 5.x is a genuine breaking change here — no default export in its ESM build, and `load()` now throws on empty input, which the global-config path relies on returning `undefined`.
- **Removed the dead image-baked `$HOME/.claude.json` onboarding shim (openlock-5wk).** Claude Code reads onboarding state from `CLAUDE_CONFIG_DIR`, never from `$HOME`, so the baked copy had no effect — and it was the stale-looking decoy that made v0.11.1's openlock-bp2 hard to diagnose. Takes effect on the next project image rebuild; no base-image change.

### Verified

- **v0.11.1's two open verification gaps are now closed empirically.** The Claude Code startup probes added for openlock-z08 were confirmed on the wire — both `GET api.anthropic.com/api/hello` and `GET platform.claude.com/v1/oauth/hello` observed ALLOWED at CC 2.1.128, against a sandbox with onboarding deliberately un-staged so the first-run path actually runs (the v0.11.1 smoke never exercised them, because openlock-bp2 pre-completes onboarding). Separately, the fork's SELinux `z`-relabel **docker** leg — which shipped podman-verified only, and which no CI can cover since both drivers' tests branch on the host's real `is_selinux_enabled()` — was verified on a Fedora host: host directory label transitioning `user_home_t` → `container_file_t:s0` (shared, no MCS category), a successful functional read from inside the container, and zero AVC denials on the bind path.

## v0.11.0

Feature release on top of v0.10.1 (fork pin v0.7.1 → v0.8.1). Adds a user-local config override layer, config/policy drift detection on reattach, and an uninstall script; closes a silent-loss-of-L7-enforcement gap and an OAuth refresh-token argv leak.

### Security

- **`openlock sandbox` no longer silently continues when the in-container proxy has lost TLS/L7 enforcement (openlock-bj2).** The supervisor falls back to a raw byte tunnel when its ephemeral TLS CA fails to generate or write at startup. In that state a session gets no `cred_inject` strip-and-replace, no per-binary secret scoping, and no content policy for its entire lifetime — only the coarse L4 allowed-IP/SSRF check still applies. The supervisor logged a Medium OCSF event and carried on, so openlock ran the session as though the moat were intact. openlock now scans the proxy log once create/reattach/recreate converge on Ready and blocks: a confirmed "disabled" state prompts `[y/N]` on a TTY (default No) and hard-exits non-interactively, while an "unknown" state (empty log, no event, or a policy that never uses proxy mode) warns and proceeds rather than being treated as either an implicit pass or a false-positive block. Credential *confidentiality* is not breached — injection simply never runs — but the anti-spoof property and all L7 enforcement are. Upstream fixed the root cause in the fork sync below; this is the host-side detection layer for the v0.7.1 pin window.

### Added

- **`.openlock/config.local.yaml` — a user-local config override layer (openlock-enk, closes GH #78).** A gitignored `config.local.yaml` sits alongside `config.yaml` and merges on top of it at sandbox load (mounts, args, env, credentials), so machine-specific settings no longer require editing the committed manifest. `openlock init` scaffolds a `config.local.yaml.example` and the `.openlock/.gitignore` entry on every init path; `openlock validate` lints the *merged* effective config so cross-file collisions surface, and renders a gitignore advisory; `openlock report` redaction now also covers credentials declared solely in `config.local.yaml`.
- **`openlock sandbox` detects config/policy drift on reattach and offers a rebuild (openlock-9or, GH #51).** On reattach openlock hashes the container's "cold" build inputs — Containerfile, mounts, policy content, the things that cannot be hot-applied to a running container — and compares them against what the session was built with. On drift a TTY gets a blocking `Rebuild? [y/N]` (default N); non-interactive runs warn and attach the stale container. `--rebuild` is now honoured on reattach (it previously warned and was ignored) and always forces a recreate regardless of drift.
- **`uninstall.sh`.** `install.sh` only ever dropped a binary, but openlock lazily creates gateway state, sandbox containers, workspace volumes, and images that only the `openlock` CLI itself can enumerate — so teardown runs *through* openlock while the binary still works, and degrades to printed manual commands when it is missing or broken. The default mode is conservative: it stops the gateway, removes the regenerable dev-build cache, and reports what remains (sessions, config, credentials, state, images) with the exact command to remove each, deliberately keeping the binary while sessions or images still reference it. `--purge` removes everything, with a blocking `[y/N]` whenever a session exists — a session always owns a workspace volume that may hold uncommitted work. `--yes` and `--dry-run` are also available (openlock-l51).
- **`openlock login` offers to persist the chosen provider as `default_provider` (openlock-4f7).** After a successful login, openlock asks whether to record that provider as the default so a later bare `openlock sandbox` resolves without a flag: Enter-to-accept when unset, Enter-to-decline when a different default is already set (never clobbers silently), and no prompt at all when it is already the default or the session is not a TTY. This does not relax the no-implicit-provider rule — the choice stays explicit. `openlock setup` opts out, since it already persists `default_provider` itself. Fixes the first-init GH #46 flow, where a preflight-triggered login previously left a lone `sandbox` invocation unable to resolve a provider.

### Changed

- **openshell fork synced to upstream: v0.7.1 → v0.8.1, 163 commits absorbed.** v0.8.0 is the first cut under the fork's release-line model — `main` is a never-rewritten mirror of upstream and the delta lives on `release/0.8`, re-authored from 24 historical commits into 5 changesets. Notable upstream behaviour now in effect: Stop/Start lifecycle RPCs carry a `workspace` field and podman resume looks the container up by label rather than a derived name; an endpoint may no longer set both `credential_signing` and `cred_inject`, because upstream's SigV4 signing computes over the pre-`cred_inject` request and allowing both would silently discard strip-and-replace (now rejected at policy load); and upstream's fail-closed TLS-CA hardening, which the Security entry above builds on. Upstream's workspace model also caps DNS-routable session/workspace names at 19 characters, down from 253 — the session-name budgeting fix below had to land first, since without it any project directory named longer than ~12 characters would have failed sandbox creation the moment the pin moved. v0.8.1 is a same-cycle follow-up: both the podman and docker drivers now default user bind mounts to the shared SELinux `z` relabel on SELinux-enforcing hosts such as Fedora — docker previously had no SELinux detection at all — plus a `cargo fmt` pass the v0.8.0 release gate had missed.

### Fixed

- **Session names are now budgeted against the fork's 19-character routable-name limit.** `friendlyNameFromId` built `<sanitized-dirname>-<6 hex>` with no truncation, leaving only a 12-character budget for the directory name; past that, `openlock sandbox` failed outright with `name exceeds maximum length (21 > 19)`. Most real project directory names would have broken sandbox creation the moment the fork pin moved. Truncation now strips an exposed trailing hyphen and falls back to `sandbox` when nothing printable survives. Only sandbox *creation* is affected — sessions already recorded under longer names stay fully usable for resume, `clean`, and drift-triggered rebuild.
- **Sandbox phase is read from `openshell sandbox get`'s structured JSON, not its human-formatted table (openlock-gr1).** The old parser ANSI-stripped colorized CLI output and regex-matched `Phase:\s*(\S+)` against a set of labels that included three branches which do not exist in the real `SandboxPhase` enum (`Running`, `Failed`, `Exited`) — and never matched `Error` at all. A sandbox in genuine failure phase therefore read as merely still-provisioning, surfacing only later when the CLI itself exited non-zero. It now uses `-o json` and reads the `phase` field directly, so `Error` correctly maps to "exited".
- **`openlock sandbox` no longer reports failure while a resumed sandbox's phase is catching up (openlock-weo).** After `openlock stop` followed by `openlock sandbox`, the resumed container could read as phase `Stopped` for up to ~35s after actually starting — the gateway derives phase from driver state gated on a container healthcheck, which lags — and the readiness wait treated that stale `Stopped` as death. Only the resume path, which just issued the Start itself, now tolerates a transient `Stopped` and keeps polling; a cold wait still fast-fails on `Stopped`, and the poll loop still performs a final strict check before giving up, so a genuinely dead-and-not-restarting container is never masked as a bare timeout.
- **The OAuth refresh token no longer appears on the command line during `provider refresh configure` (openlock-axb).** It was passed as `--material refresh_token=<value>`, putting a long-lived credential into argv and therefore into world-readable `/proc/<pid>/cmdline`. It now goes via `--secret-material-env refresh_token=<ENVVAR>` and the spawned process's environment, mirroring the `--credential` pattern fixed in v0.10.1. `client_id`, which is not secret, stays on `--material`. This completes the deferred half of the v0.10.1 entry — no fork change was needed, since the flag already existed upstream.
- **`openlock clean` self-heals the gateway before classifying sessions, not per-session (openlock-kx8).** A down gateway previously made `clean` fail outright with a raw `Connection refused`. Healing *before* the bulk classification pass rather than per-session is what makes this safe: `classifyAll` maps any transport error to "missing", so per-session healing would have misclassified every healthy session as missing while `--stale` targets `exited || missing` — destroying live sandboxes. If bring-up fails the bulk path now aborts before classifying, rather than acting against a gateway known to be down. With no runtime resolvable at all, teardown skips the gateway-mediated delete and reaps local bookkeeping directly, warning that a container may remain. (The underlying `getSandboxState` conflation of "gateway unreachable" with "sandbox missing" is tracked as openlock-vtl.)
- **`openlock doctor` no longer assumes `apt`, and catches a missing `cmake` in dev mode (openlock-3o7, openlock-e7q).** The install hint fell back to Debian-specific `apt install <pkg>` across all of Linux, giving wrong advice on Fedora, RHEL, and Arch; the Linux hint is now package-manager-neutral, while macOS keeps `brew install` as a safe assumption. Separately, a dev-mode gateway build now needs `cmake` (upstream's bundled z3 build invokes it) and previously died deep inside a long `cargo build` with a late, confusing error — `doctor` now checks for it up front, gated to dev mode only.
- **The gateway's generated config now sets `enable_bind_mounts` (openlock-4sh).** Upstream gates driver-config bind mounts behind an operator flag defaulting to false; without it both the podman and docker drivers hard-error on any bind mount issued through the upstream driver-config path. This is harmless today because `--volume` uses its own bespoke bind-mount path, but it unblocks migrating `--volume` onto the upstream mount system. Takes effect on the next `openlock gateway stop && start`, since the config is only rewritten when the gateway is not already running.

### Docs

- **README's "How it works" no longer describes a model that was removed (openlock-1tn, GH #50).** The pre-init capability-detection step (js/py → image + policy) no longer exists, and the gateway builds from source on first run only in dev mode, not in releases.
- **`docs/policies.md` documents the fork's `cred_inject` extension end to end (openlock-ntu, GH #50)**, against the existing `GITHUB_TOKEN` example, and links OpenShell's upstream security-policy reference.
- **New permissions-disabled recipe and rootless-podman Linux setup (GH #73, GH #49).** Covers `--dangerously-skip-permissions` inside the sandbox, and subuid/subgid setup including the widen-while-in-use footgun.
- **`docs/agent-config-reference.md`'s manifest key list now includes `harness` (openlock-c0c)**, which was missing despite being present in `MANIFEST_KEYS`.

## v0.10.1

Bugfix release on top of v0.10.0 (fork pin unchanged at v0.7.1). A post-release bug sweep of the credential, report, and sandbox-lifecycle paths.

### Added

- **`openlock sandbox --rebuild` forces a fresh image build.** The cached-image short-circuit keyed on the Containerfile hash, so a mutable third-party `FROM` tag (same Containerfile ⇒ identical hash) could never be refreshed without a manual `podman rmi`. `--rebuild` bypasses the cache (`--no-cache --pull`) to pick up the newer base; it warns and is ignored when reattaching to an existing session (image is fixed at creation).

### Fixed

- **Shell injection via `.openlock/config.yaml` mount paths (HIGH).** Mount source/target values from config were interpolated **unquoted** into the `bash -c` sandbox-setup script, so a crafted git-bundle target (e.g. `/sandbox/.openlock/x$(...)`) ran arbitrary commands at container-create time. All config-derived values are now single-quoted; a behavioral test executes the generated script and asserts no injection fires (including odd-but-legal space/colon targets).
- **Injected credentials could leak into `openlock report` bundles.** A secondary credential injected under a custom header matches no shape/header redaction regex, so its value could survive in the bundled `gateway.log`. Report generation now literal-redacts the actual known secret *values* (stored provider creds, refresh tokens, and `credentials:` bundles resolved from host env), and never throws on an unset bundle env var.
- **Credential secrets no longer appear in `/proc/<pid>/cmdline`.** Provider provisioning and cred-refresh passed `KEY=VALUE` in the spawned `openshell` argv, exposing tokens in the world-readable process command line. The secret is now handed to the child via its environment and only `--credential KEY` appears in argv. (The fork's `refresh_token` via `--material` still requires `KEY=VALUE` and is deferred — openlock-axb.)
- **`openlock sandbox --no-attach` no longer orphans the sandbox.** The gateway was spawned without its own session, so a SIGHUP when the short-lived scripted CLI exited killed the gateway too — leaving a healthy container that later `sandbox`/`clean` calls couldn't reach ("no container" / transport error). The gateway is now spawned detached (`setsid`, own session) so it survives however the CLI exits, and reattach starts the gateway *before* querying sandbox state so a dead gateway self-heals instead of masquerading as a missing container.
- **`openlock report` recorded zero sessions.** It read session state from `state.json`, but the session store writes `meta.json`; bundles always showed no sessions. It now reads `meta.json`.
- **`git-sync` no longer masks a real sync failure as "nothing to do".** A failed bundle/download drain of in-sandbox git work printed the same `No commits to sync.` as a genuinely empty repo (stderr was discarded). Stderr is now captured and genuine failures are reported distinctly.
- **`prune-images` reports only images actually removed.** It printed the full candidate list as "removed" even when `image rm` failed; it now checks each removal's exit code, lists real failures separately, and exits non-zero on failure.
- **Broadest egress patterns are now flagged.** The policy wildcard lint (`checkTldWildcard`) missed a bare `*` / `**` match-all host — the widest possible allow rule. It's now flagged, with the message generalized to "overly broad host wildcard".
- **`openlock doctor --help` prints usage** instead of running the full check suite.
- **Preflight surfaces its gateway-reachability probe.** The (already-computed, ≤15s) reachability result was discarded; it's now surfaced as a warning.
- **Uncaught async dispatch errors print cleanly.** A global `unhandledRejection` handler makes lazy `import().then(cmd)` command branches surface `openlock: <msg>` + exit 1 instead of a raw Bun stack dump. Also removed dead code: the unused `git bundle create` in `clean --copy`, the never-read `clean --json` flag, and corrected a global-config docstring that overclaimed cross-process TOCTOU safety.

## v0.10.0

### Added

- **A sandboxed `claude_code` harness can now bill your Claude subscription instead of the API.** `openlock login --provider anthropic` runs a host-side OAuth PKCE flow (hosted paste-back callback, no localhost listener) instead of `claude setup-token`, storing a real access+refresh token pair. At sandbox start the sandbox receives a dummy OAuth-shaped `.credentials.json` — flipping Claude Code into OAuth mode — while the gateway strips any `Authorization` header and re-injects the real bearer token at egress; the real token never enters the sandbox. `openlock sandbox --no-attach` supports headless import-from-CC-login flows. Breaking: a legacy v1 setup-token credential is dropped (lossy) on migration to the new credential shape — re-run `openlock login`; and `opencode` no longer supports the `anthropic` provider (subscription billing is `claude_code`-only — use `openrouter` or the OpenCode Claude-auth plugin).
- **`openlock logs <name>` surfaces the in-container proxy's egress log.** Tails the supervisor's OCSF audit log (`/var/log/openshell.<date>.log`) for per-request L7 allow/deny decisions (method, URL, policy, engine, calling binary) — visibility neither the host gateway log nor echo mode provided. `-f`/`--follow` streams, `-n`/`--lines` bounds it (default 200). An opt-in `--debug-egress` flag on `openlock sandbox` (fork v0.6.6+) raises the supervisor's log level to debug so `openlock logs` also shows L7 request/response **headers** (e.g. `anthropic-beta`, `overage-status`) — useful for confirming which billing bucket a request landed in. Off by default; applies at container creation, so reattaching keeps the session's existing log level.
- **Config-driven secondary credential injection.** A `credentials:` key in `.openlock/config.yaml` lets a sandboxed agent authenticate to third-party services (e.g. `GITHUB_TOKEN` → `api.github.com`) with the same protections as the primary provider credential: the value is read from a host env var at run time (`{ from_env: VAR }`), provisioned as a generic gateway provider, and injected at egress per-binary-scoped by `policy.yaml` — it never enters the sandbox environment or gets committed. `openlock validate` now hard-errors when a policy's `cred_inject` references a credential no attached provider supplies, or when a bundle name collides with a built-in provider. Providers attach at session-create time; adding a bundle to an existing session requires recreating it.
- **Opt-in idle-sandbox reaper (`reap_idle`, default off).** Previously, exiting `openlock sandbox` silently SIGKILLed *every* unattached-but-running sandbox across all projects after 30 minutes, with no git drain — a global side effect with no way to opt out (GH #76). Reaping is now off by default; a `reap_idle` global-config key (`off`, or a duration like `30m`/`2h`/`1d`; `OPENLOCK_REAP_IDLE_MS` env overrides) opts back in, and session-end now prints an advisory nudge listing other idle-unattached sandboxes when reaping is off, instead of touching them. When reaping is enabled: `lastAttachedAt` is now a live heartbeat (refreshed on a `min(idleMs/2, 60s)` cadence while a harness is attached) rather than a stamp frozen at attach time, so a killed CLI or dropped SSH session no longer makes an actively-used container look idle-stale; the reaper now gracefully drains in-sandbox git state (best-effort bundle sync-back) before stopping a session instead of hard-killing it; and the sessions about to be reaped are logged before the stop loop runs, not just counted afterward.

### Changed

- **openshell fork synced to upstream (fork v0.7.0, later pinned to v0.7.1): 133 commits absorbed.** The fork caught up to NVIDIA/OpenShell after a long gap (base 2026-05-26), absorbing upstream's split of the monolithic `openshell-sandbox` crate into separate `openshell-supervisor-network` (egress proxy, L7, OPA) and `openshell-supervisor-process` (landlock, netns, seccomp) crates. openlock's cred-inject + trust stack was re-homed into the network crate accordingly. No openlock CLI surface changed; sandbox creation, credential injection, and egress enforcement behave as before. Validated on macOS (podman-machine) and a native rootless-podman Linux box. v0.7.1 adds a single follow-up commit gating the gateway's `Sandbox failed to become ready` warning on the transition *into* `Error`, instead of re-firing it every 60s reconcile pass over an already-dead sandbox — the dominant driver of the unrotated `gateway.log` growth described below (GH #76).
- **Sandbox `stop` / resume now works on native Linux.** With upstream's Stop/Start RPC plumbing in place, `openlock stop <session>` followed by re-running `openlock sandbox` reliably resumes the container on native rootless podman. (A resume hang remains on the macOS podman-machine VM — tracked separately; it does not affect Linux hosts.)

### Fixed

- **The gateway builds with static-linked z3 (fork v0.7.0).** Upstream gave `openshell-server` a prover dependency that pulls `z3-sys`, so the gateway now links z3. Both the release build and openlock's dev-mode build-from-source compile it with `bundled-z3` (no runtime `libz3` dependency), matching the existing CLI build. Building the gateway from source on a fresh Linux box additionally requires `cmake` (GitHub CI runners and typical dev machines already have it).
- **`openlock init --harness <name>` choices actually stick.** The scaffolded `.openlock/config.yaml` never recorded the chosen harness, so a bare `openlock sandbox` afterward silently fell back to the hardcoded `claude_code` default and failed with a confusing `No provider selected for harness 'claude_code'` — naming the wrong harness. `init` now writes a `harness:` key, read back at sandbox launch ahead of the global `default_harness` (still overridable via `--harness` / `OPENLOCK_HARNESS`).
- **`openlock init --harness opencode` no longer scaffolds a dead OpenRouter model slug.** The commented example model had rotted (404) since free models on OpenRouter change over time; the scaffold now points at the live filtered model list instead of pinning a slug that will eventually rot again too.
- **`gateway.log` no longer grows unbounded.** The gateway's captured stdout/stderr was appended to forever across restarts — observed at 100MB (GH #76), driven mostly by the fork-side reconcile-loop warning described above. openlock now rotates the file to a single `.1` backup generation whenever it's grown past 10MB, checked at each gateway (re)start; rotation failures warn but never block startup.
- **`openlock sandbox` create/resume failures now surface their real cause (GH #75).** When a sandbox container exits during provisioning — most commonly because a host firewall/network reload flushed the netavark NAT rules a bridge-network container needs to reach the gateway — openlock used to burn its full poll timeout and report a misleading `staging upload … not visible within 30000ms`. It now fails fast with the supervisor's actual log line, falling back to a network-reachability hint when the container died before it could push any logs to the gateway. `openlock doctor` gained a reachability check that reproduces the exact container→gateway path (a throwaway container on the `openshell` network probing the gateway port): suggest-only by default (`podman network reload --all`), with a new opt-in `network_auto_reload: true` config to run the reload automatically. A related Linux-only, warn-only check now flags a gateway that came up bound to `127.0.0.1` only, since a plain readiness probe can't tell that apart from a correct wide bind. (The JWT-expiry-on-resume half of the original report turned out to already be fixed upstream — fork v0.7.1's local sandbox JWTs never expire — so no code change was needed there.)

### Changed

### Fixed

- **`doctor` and sandbox preflight catch an insufficient rootless subuid range.** On rootless podman (Linux, non-root), openlock now reads `/etc/subuid` and verifies the user's range covers the sandbox UID; if not, it fails legibly with a `sudo usermod --add-subuids …` fix hint up front instead of dying later at the upload with `Permission denied`. Skipped on macOS, docker, and rootful/root podman.
- **The agent owns its HOME subtree in the sandbox.** The per-project image now reclaims ownership of `/sandbox` after the root-run harness install, so the agent can write `~/.local` / `~/.config`. This fixes opencode's `unable to open database file` on a fresh sandbox, where `/sandbox/.local` had been left root-owned.
- **`doctor` no longer false-negatives when both podman and docker are installed.** The non-interactive runtime resolver only auto-picks when *exactly one* runtime is present; with both installed it returned `null`, which `doctor` rendered identically to "no runtime installed" (a misleading `✗ container runtime (podman/docker)` with an "install one" hint). `doctor` now probes both and reports **every** installed runtime plus its readiness (podman API socket / docker daemon / podman machine on macOS), so a host with both shows both. Session preflight still checks only the runtime it resolved.

These suites now neutralize `XDG_CONFIG_HOME` in setup like the already-correct ones, keeping the suite hermetic.

- Default policies (`policies/default*.yaml`) now include an `opencode` block with both `api.anthropic.com` (x-api-key cred_inject) and `openrouter.ai` (Authorization Bearer cred_inject) endpoints. Per-binary cap-aware binaries (claude+node / claude+python3 / claude+node+python3) preserved.

### Deprecated

- For the `claude_code` harness with no provider signal AND a stored anthropic record, openlock auto-selects `anthropic` and prints a one-shot deprecation hint. The auto-default is removed in v0.8.0; users should set `--provider`, `OPENLOCK_PROVIDER`, or `default_provider:` to silence.
- Legacy `readToken()` / `writeToken()` shims in `src/tokens.ts` are removed in v0.8.0.

## v0.6.0

### Breaking

- **Mount system v2.** `.openlock/config.yaml` `mounts[]` now supports four types: `copy-once`, `copy-refresh`, `bind` (live `podman -v` passthrough), `git-bundle` (host repo bundled in + cloned in container). The workdir mount at `/sandbox/repo` is now **optional**; absence yields an empty `/sandbox/repo`. Existing configs that depend on the prior bundle-of-`projectPath` behaviour must add an explicit `git-bundle` workdir mount:
  ```yaml
  mounts:
    - source: .
      target: /sandbox/repo
      type: git-bundle
  ```
  See README "Seeds: mounts, args, env" for the full type matrix + examples.
- Fork pin bumped to [`vessux/OpenShell` v0.4.0-rc.1](https://github.com/vessux/OpenShell/releases/tag/v0.4.0-rc.1) for `--volume` + auto userns-remap on rootless podman.

### Added

- `--branch <name>` flag on `openlock sandbox`. Honoured for `git-bundle` workdir (clones with `-b <branch>`); rejected (exit 2) for `bind`/absent workdir with explanatory stderr.
- README: 6 worked examples covering workdir + non-workdir cases; security/ownership/VM-driver notes for bind.

### Fixed

- Image-level provisioning of `/sandbox/repo` so openshell's PID 1 chdir succeeds even when no workdir mount is declared (PR #30).
- `createSession` waits for openshell's async `--upload` to land in `/sandbox/.openlock/` before tearing down the staging tmp dir (race surfaced when container start got faster with the image-level mkdir).
- Bundle clone idempotency check uses `[ -d ${target}/.git ]` instead of `[ -d ${target} ]` so the image-baked empty `/sandbox/repo` doesn't suppress the first clone.

### Known limitations

- `cleanSession --copy-dir` hardcodes `/sandbox/repo` + `/sandbox/out.bundle` paths; under bind workdir it produces redundant bundle work, under no-workdir-mount it produces an empty copy. Deferred to post-v0.6.0 cleanup.

Fixes discovered during smoke that landed in PR #30:
- Image-level `/sandbox/repo` provisioning.
- Staging-upload race wait.
- Bundle clone idempotency check (`.git` instead of dir).
- Fork pin bump v0.3.0 → v0.4.0-rc.1.
- README: bind log example moved to `/home/sandbox/logs` (avoid `/sandbox/.openlock/` upload collision).
- **Gateway `--bind-address 0.0.0.0` on Linux** — on rootless podman, containers see `host.containers.internal` as the slirp4netns/pasta gateway IP (not loopback), so the gateway must bind a non-loopback interface. Mac unaffected (podman-machine VM bridges back to host 127.0.0.1).
- **Sandbox uid 999999 in `openlock-core` images, with numeric `USER 999999:999999` directive** — picks a uid that fits both macOS podman-machine's default subuid range (100000-1099999) and Linux's typical 524288+ range. The openshell fork parses `Config.User` as numeric and applies `--userns=keep-id:uid=N,gid=N` when any bind mount is present, so the in-image sandbox uid must match for host-owned bind sources to be writable from inside the container on Linux. Without this, container→host writes failed with EACCES on rootless podman.
- **CI: live integration job** — `.github/workflows/test.yml` now runs `tests/integration/` under `OPENLOCK_LIVE_INTEGRATION=1` in a separate job after the unit-test pass. Keeps local `bun test` fast (3 integration tests still skip without the env var) while ensuring the gated tests never silently regress.
